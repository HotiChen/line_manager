# 💡 產品立項與拆解流程 (Epic Planning Flow)

此工作流 (Workflow) 負責處理從「商業點子發想」到「產生工程師工作清單 (Tickets)」的完整生命週期。它會依序啟動產品經理、系統架構師與技術組長，為專案打下最堅固且具備商業價值的地基。

## 🎯 運作流程與接力順序

當您輸入任務描述與點子後，系統將自動依序執行以下步驟：

1. **👩‍💼 `/product-manager` (產品經理) 進行靈魂拷問與市場驗證**
   - 審查您的輸入點子，並給予精闢、犀利的「吐槽」與可行性分析。
   - 利用 `search_web` 調查競品狀況、市場缺口與商業變現潛力。
   - 產出極簡但極高商業價值的產品需求文件 (PRD)，並定義第一版的 MVP 範圍（以「零學習成本」為標竿）。
   - 📄 **產出文件**: `docs/PRD.md` (包含商業護城河、MVP 規格與零學習成本指南)

2. **🏛️ `/system-architect` (雲端系統架構師) 接手設計架構**
   - 閱讀剛才的 `docs/PRD.md`。
   - 根據 MVP 預算與流量預估，提出最具 C/P 值 (FinOps) 的雲端部署架構設計。
   - 繪製資料庫實體關聯圖 (ERD / Database Schema)。
   - 針對金流或敏感資料，事先定義身分驗證、RBAC 權限與 API 金鑰隔離等資安規範。
   - 📄 **產出文件**: `docs/ARCHITECTURE.md` (包含 ERD、系統架構圖與 API 端點規劃)

3. **📋 `/task-planner` (技術組長與任務拆解) 產出工單**
   - 接收 `docs/PRD.md` 與 `docs/ARCHITECTURE.md`。
   - 將龐大的藍圖拆解為能給其他 AI 專家執行的「原子化任務清單 (Task Tracker)」。
   - 為每一個小任務定義「負責的專家角色」與「明確的驗收標準 (Acceptance Criteria, AC)」。
   - 📄 **產出文件**: `docs/task_tracker.md` (這是接下來 `/build-feature` 開發工作流的核心依據)

## 🚀 使用方式

在開始一個全新的點子，或是大改版時使用：

```
/start-epic 我們要做一個專門針對寵物美容院的線上預約 SaaS，希望有 LINE 結合跟無現金支付，幫我分析並建立架構。
/start-epic 我想做一個類似 Notion 但專注於寫長篇小說的網頁工具，預計採訂閱制。
```

> **⚡ AI 行為準則**: 
> - 如果 PM 覺得點子真的完全不行，請先暫停後續的架構師流程，並詢問 USER 的想法。
> - 在每個專家完成他們的工作後，**必須明確創建出指定的 `.md` 檔案 (保存在 `docs/` 或專案根目錄下)**。
> - 第一步產出後，等待 USER 同意後再自動執行架構設計與任務拆解。避免過早落實錯誤的方向。
> - 下游工作流 (例如 `/build-feature`) 將完全依賴這裡產出的 `docs/task_tracker.md` 進行推進，所以格式必須標準化。
