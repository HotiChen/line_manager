# 🚨 緊急救火隊伍流水線 (SOS Emergency Flow)

這是所有開發者最不想用到、但必備的 Workflow。
當正式環境 (Production) 湧入大量客訴、出現 502 Bad Gateway 或是莫名其妙的 "Heisenbug" 時，不要漫無目的地進去看 Code。這個工作流會啟動最冷靜的三人調查小組，科學化地找出崩潰點並提供解法。

## 🎯 運作流程與聯合調查順序

遇到連線異常與抱怨時，直接叫出此工作流，系統會依序執行：

1. **🎧 `/support-agent` (24/7 客服員) 案情釐清與安撫**
   - **核心任務**: 面對使用者模糊的抱怨 ("不能付款啦！")，第一時間回覆安撫。
   - **調查任務**: 梳理使用者的環境條件 (OS, 瀏覽器版本)，並詢問具體操作步驟，過濾掉「單純是客戶不會按介面」的假警報。
   - **產出**: 一份結構化的 `docs/bug_report_ticket.md`。

2. **🕵️ `/deep-debugger` (系統除錯專家) 科學診斷**
   - **核心任務**: 接收從客服端遞交的 Bug Ticket。
   - **強制五步法**: 絕對不准瞎猜！強制遵守「重現 -> 隔離 -> 假說 -> 修復 -> 驗證」。
   - **排查動作**: 讀取伺服器報錯的 Logs，追蹤 Stack Trace，假設是前端全域變數互相覆蓋 (Race condition)、還是後端 null 指標異常。找出 Root Cause (根因)。

3. **🚀 `/perf-optimizer` (效能優化專家) 瓶頸排查 (若 Bug 屬於效能問題)**
   - **核心任務**: 很多時候當掉不是因為寫錯 Code，而是「塞車」了。
   - **調查任務**: 檢查是不是因為這波湧入的訪客觸發了資料庫的 N+1 Query，導致連線池 (Connection Pool) 爆炸。或者是前端忘記清空計時器導致 Memory Leak 把瀏覽器卡死。
   - **產出**: 提供緩存 (Cache / Redis) 或撰寫輕量化代碼的應急處方箋。

## 🚀 使用方式

當大火燒到後院時，毫不猶豫地呼叫：

```
/sos-emergency 收到三筆客訴說結帳到一半畫面會全白，這是我剛拉出來的 error.log，請立刻排查原因並給出修復方案。
/sos-emergency 首頁載入時間突然飆高到 10 秒，幫我找出是哪個新上的功能導致的效能瓶頸。
```

> **⚡ AI 行為準則**: 
> - **絕不盲目改 Code (Read-Only Investigation)**：在沒有確認 100% 能重現問題且找到 Root Cause 之前，這條流水線的專家不准提議去修改任何生產環境的程式碼。
> - **提供熱修復方案 (Hotfix Strategy)**：若找到 Bug 所在，立即提供可以閃電打補丁 (Hotfix) 的修復代碼，並強烈建議 USER 必須將這些修好的 Code 送進 `/qa-deploy` 工作流進行迴歸驗證。
